# Consensus peer score arithmetic

This batch fixes two arithmetic defects in restored consensus peer history. The
existing scoring weights, address selection policy, failure resets and persisted
cache schema remain unchanged. Source `a134d127` is independently reviewed;
all seven local workspace gates pass. PR/CI completion remains pending.

## Findings

- **B3-33 — address score overflow and narrowing (P2, fixed):** address successes
  and failures are stored as unrestricted `u32` values. Ranking converted them to
  `i32` before multiplying by 100 and 125. Large counts could overflow arithmetic;
  counts above `i32::MAX` changed sign during conversion. Checked builds could
  stop on overflow, while wrapped arithmetic could invert address preferences.
  The cache loader restores these values directly, so a valid saved large count
  reaches ranking without first accumulating that history in the current process.
  An offline cache/reopen control selected a repeatedly failing address ahead of
  a successful address on the original code.
- **B3-34 — success can erase saturated peer history (P2, fixed):** status,
  bootstrap and useful-response counters are also restored as `u32`. Their plain
  increments overflowed at the maximum. Wrapping to zero could remove usefulness
  and preferred-peer credit; checked builds stopped instead. A cache/reopen
  control reproduced the increment failure and now covers every RPC kind.

These are demonstrated numeric-boundary defects. The audit did not observe them
in a live deployment or establish that an ordinary remote response can directly
choose the persisted values.

## Correction and invariants

Compute address scores in `i64`, converting each input before arithmetic. The
entire existing weighted `u32` domain fits exactly: valid scores range from
−536,870,911,725 through 429,496,729,900. Propagate the wider score through its
private wrapper and use a lower `i64` fallback for an unclassified address.
Comparators, family filtering, lexical ties and address-count limits are unchanged.

Saturate the three persisted lifecycle success counters at `u32::MAX`. Existing
transport/disconnect resets and useful-response backoff recovery still run after
the counter update. Address counters already saturated and required no change.

The separate peer-level score remains safely bounded by its existing usefulness
and failure clamps and the actual support scores generated by its caller (0–5).
Widening that score or changing the lifetime weighting policy was unnecessary.

The correction adds no allocation or persistence operation. It changes constant
size arithmetic in peer bookkeeping and address sorting, with no new work in the
log-row processing path. No throughput claim or new benchmark campaign is made.

## Regression evidence and validation

Four controls failed against baseline `0d5bec37` and pass after the correction:

1. Independent literal scores around the old multiplication/signed-conversion
   boundaries and at the complete counter extrema, including mixed history.
2. Monotonic success/failure ranking for all four address classes in both
   bootstrap modes, using a small fixed set of counter boundaries.
3. Saturated lifecycle counters restored through the real peer-cache writer and
   loader, preserving preferred status and peer-level priority for every RPC kind.
4. Restored large address history passed to actual address selection, including
   both bootstrap modes and the unclassified-address fallback.

Fixtures use temporary directories and unpolled network objects. They do not
start discovery, open listeners or contact peers. Three test-only conversions to
`i64` enabled the baseline's `i32` return type; those redundant conversions were
removed after widening, without changing expected results or assertions.
