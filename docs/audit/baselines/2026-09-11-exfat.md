# Isolated ExFAT validation — 2026-09-11

The existing external volume on `mac-mini` was inspected through read-only
volume metadata only. Its contents and production service were not changed.
The user explicitly authorized source transfer and isolated tests after the
initial automatic approval review blocked transferring the private repository.

## Environment and isolation

Source revisions `09a63f55` and `ff728ea3` were exported into separate new
directories under a task-owned `/private/tmp` directory on the system disk.
The host is an Intel Macmini8,1 with six logical CPUs, 16 GiB RAM and macOS
15.7.9 / Darwin 24.6.0. Both builds use the pinned `nightly-2026-08-24` compiler,
Rust commit `fb6531d550e0075b9eb9a51464f404805eec87d9`, and locked dependencies.
Compilation uses two low-priority workers and a separate task-owned target
directory. The existing system-disk dependency cache lacked two locked packages;
Cargo fetched them without changing the lockfile.

Creating an ExFAT `SPARSE` image returned `Operation not permitted` on both
hosts. Creating a blank `UDIF` image succeeded. No system protection was changed.
A new 512 MiB image was mounted at a private staging mountpoint with `-nobrowse`;
it is backed by the internal APFS filesystem and has a 512-byte allocation block.
This establishes an isolated ExFAT test environment, not external USB hardware
performance or physical power-loss behavior.

The image creation procedure, using newly allocated staging paths, is:

```sh
hdiutil create -size 512m -fs ExFAT -type UDIF /staging/exfat.dmg
hdiutil attach -nobrowse -owners off -mountpoint /staging/exfat /staging/exfat.dmg
```

## Correctness results

The `ff728ea3` storage unit-test executable ran with `TMPDIR`, `TMP` and `TEMP`
pointing to the disposable image. Its temporary directories were observed on
that mount while the suite ran. **117 tests passed, zero failed, one explicit
WAL benchmark was ignored.** This includes the main-thread I/O failure matrices,
historical staging/compaction recovery, process-exit recovery, malformed WALs,
canonical preservation, locks and symlinks. The suite took 588.45 seconds;
another low-priority build ran concurrently, so this duration is not a performance
comparison. [Recorded environment and results](2026-09-11-exfat.json).

Generic compatibility probes on the image also accepted ordinary `fsync`,
`F_BARRIERFSYNC`, `F_FULLFSYNC` and exclusive locks for files and directories.
These are syscall acceptance checks, largely on already-flushed files. Their
timings must not be interpreted as ingestion throughput or evidence of physical
media persistence after power loss.

A new explicitly ignored test,
`native::storage::tests::checkpoint_recovery_across_distinct_mounts`, passed
locally using a separate disposable ExFAT image and an APFS staging directory.
It checks the actual device IDs rather than substituting a fake device number.
Eight combinations cover both placement directions, WAL-file and segment-directory
aliases, and live/historical ingestion. They close with a pending checkpoint,
reopen, rotate segments, reopen again and compare every recovered row exactly.
Apple test events confirm that the cross-device full-sync branches execute;
recovery leaves an empty WAL and no journal. Only new `TempDir` children of the
two supplied roots are changed. The two mounted filesystems share underlying
physical storage; this is not a two-drive power-loss test.

After adding this test, all six required local workspace gates pass: 823 tests,
zero failures and five explicitly ignored tests. The additional ignored test was
run separately as described above. [Gate results](2026-09-11-exfat-gates.jsonl).
All six Linux/macOS CI jobs passed for the production candidate `ff728ea3` in
run `34520575847`; the newly added test still needs CI on its own commit.

To repeat on two disposable staging roots on distinct mounts:

```sh
LOGEX_TEST_VOLUME_A=/staging/system \
LOGEX_TEST_VOLUME_B=/staging/exfat \
cargo test -p logex-storage --lib --locked \
  checkpoint_recovery_across_distinct_mounts -- \
  --ignored --nocapture --test-threads=1
```

## Release comparison

Five alternating baseline/candidate process pairs per dense/sparse profile, with
three iterations per process, completed on the disposable image. All independent
row/query/lifecycle oracles passed. The unchanged fixtures use 200,000 rows,
8,192-row calls, 50,000-row segments and four query workers; candidate final
checkpoint costs are included. Fresh directories are used for writes; caches
are not evicted, and queries are warmed once. No audit build or test ran during
timing; the existing host workload was not controlled.

The image sits on the internal disk, so neither the absolute timings nor their
difference measure the existing USB volume. Compare revisions on this host;
do not compare its Intel/image timings directly with the ARM/APFS host.
