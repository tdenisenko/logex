# Beacon decode comparison — 2026-09-09

Baseline: `f9f2d49e`. Candidate: the implementation in the beacon SSZ audit PR,
with production-section SHA-256 and executable hashes in the
[final raw samples](2026-09-09-beacon.jsonl). Runtime source was unchanged after
measurement; the additional byte-hash equivalence test is outside that hash.

## Environment and workload

- Mac14,15, 8 logical CPUs, 16 GiB RAM; aarch64 macOS 26.6.2 (25G83), internal
  APFS storage, about 154 GiB free. Ordinary desktop session, no CPU isolation
  or simultaneous builds during timings.
- Pinned nightly-2026-08-24: rustc 1.100.0-nightly `fb6531d55`, Cargo
  1.100.0-nightly `e8cb624d5`. Same lockfile and default release profile.
- `beacon_block_14132042.ssz`, 205,273 bytes; SHA-256
  `229c2f223d208f6cdc60dbbf29359715c99323946020cef9ca4a5dae1a0e0cb4`.
  Compiled into the executable, copied into memory once.
- Each process performs 10 warm-up decodes and five samples of 200 decodes.
  Five process pairs alternate baseline/candidate ordering: 10 processes,
  25 samples per version, 10,000 measured decodes total. Every decode asserts
  the canonical root. Input is black-boxed; timed work includes decoding and
  existing full root/anchor computation, with no disk or network I/O.
- macOS `/usr/bin/time -l` reports whole-process maximum RSS. These timings do
  not represent network sync, decompression, signatures, storage or queries.

## Final results

Times are per-decode averages within 200-decode samples. The nearest-rank p95
is for these batch averages, **not** individual-request tail latency.

| Metric | Baseline | Final candidate |
| --- | ---: | ---: |
| Median decode + commitments | 2.9426 ms | 3.0461 ms |
| p95 batch average | 2.9741 ms | 3.0965 ms |
| Median whole-process peak RSS | 8,257,536 bytes | 8,192,000 bytes |
| Maximum whole-process peak RSS | 8,290,304 bytes | 8,224,768 bytes |

The retained change costs **3.52%** at the median on this fixture: an explicit
correctness tradeoff for bounded decoding, consistent list limits and context
validation, not a speedup. It is below the plan's 5% investigation threshold,
but is reported rather than described as noise. Memory stayed comparable.
One block is not a representative full-chain workload; deposit-bearing blocks
are correctness fixtures and were not timed.

## Investigated regression

The fully derived execution-payload variant measured 2.9741 ms baseline versus
6.1907 ms candidate (about 2.08x); its
[raw samples](2026-09-09-beacon-derived.jsonl) are retained. Inspection of
`ssz_types` 0.11.0 `vec_tree_hash_root` showed a packed-hash write per byte.
Restore contiguous byte-slice hashing for extra data and transactions, retaining
bounded SSZ field types as the source of Merkle depth. Other containers keep
derived hashing. Chunk-boundary tests match the direct roots against generic SSZ
hashing, and the real fixture retains its canonical root. No check is weakened.

An earlier attempt reused the baseline executable for both labels because Cargo
considered it fresh in a shared target directory. Equal binary SHA-256 and missing
candidate test names exposed the problem. Those samples are excluded from both
datasets. Cleaning only the consensus crate's release artifacts forced a genuine
candidate rebuild. Subsequent hashes differed and test inventories were checked.

## Reproduction

```sh
cargo test -p logex-cl --release --lib --locked \
  beacon_block::tests::beacon_decode_release_baseline -- --exact --ignored --nocapture
```

For a comparison, build both revisions with this identical benchmark function,
copy their emitted test executables to separate paths, and run each with the
same filter/flags under `/usr/bin/time -l`. Alternate order for five pairs and
retain JSON samples and RSS output. Build before timing. Use separate target
directories or invalidate crate artifacts when changing checkouts; **verify
executable hashes and test inventories**, not just Cargo's exit status. The
baseline adds the unchanged benchmark function to its existing beacon test module.

This focused harness supplements storage/query benchmarks; it does not replace
integrated regression or staging.
